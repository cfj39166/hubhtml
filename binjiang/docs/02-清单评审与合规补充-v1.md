# 清单评审与合规补充 v1

> 项目：社区 · 邻里服务
> 日期：2026-11-06
> 对象：[01-功能点清单-v1.md](01-功能点清单-v1.md)
> 结论：清单整体闭环成立，"风险分级 + 楼栋运营 + 证据链"三条主线清晰。但有 **1 个内部不一致缺口、3 个落地合规风险**，直接影响 P0 的实现方式和上线合法性，需要纳入基线。

---

## 一、清单内部一致性缺口

| 缺口 | 问题 | 建议 | 优先级 |
|---|---|---|---|
| **站内沟通缺失** | 五-"证据链留存"要求"聊天记录统一归档"，但清单里没有任何聊天/沟通功能点。居民发布前必然要咨询细节，如果沟通发生在微信私聊，证据链恰好在最关键的一环断掉，纠纷时平台拿不到记录 | 新增"**站内订单沟通（轻量版）**"：仅订单双方可见的订单关联留言；敏感词与站外联系方式过滤（引导在平台内完成交易与沟通）；消息记录随订单归档进证据链。冷启动先做留言板形态，不做实时 IM | **P0** |
| **用户侧隐私告知同意缺失** | 五-"隐私与权限分级"只覆盖内部权限（协调人只看本楼、门牌接单后可见），没有覆盖对居民的告知同意。清单收集身份证、健康信息（宠物/陪诊）、儿童信息（接娃）、位置，均为 PIPL 意义上的敏感个人信息 | 新增"**隐私政策与单独授权**"：首次注册告知同意；健康申报、儿童信息等敏感字段单独授权，儿童信息必须由监护人填写；数据最小化收集；提供注销与删除入口 | **P0** |
| 服务者端通知未单独列出 | "消息通知"列在用户端，但服务者端同样依赖接单、结算、资质到期通知 | 归并为公共能力，四端复用同一通知服务；不新增开发量，仅基线归属修正 | P0（合并，不新增） |
| 后台操作审计缺失 | 信用规则修改、纠纷责任判定、楼栋开通开关都是高影响敏感操作，无审计则内部风险不可追溯 | 新增"**后台操作审计日志**"：关键配置变更与判定操作记录操作人、时间、前后值 | P1 |

## 二、外部落地风险（不改变功能范围，但决定 P0 的实现方式）

| 风险 | 说明 | 建议实现方式 |
|---|---|---|
| **支付"二清"合规**（最高优先） | 清单要求"完成后即时到账服务者，平台低抽成"。若货款先进入平台自己的账户再转给服务者，构成无证从事支付结算业务（"二清"），是央行监管红线，也是平台最大的法律风险 | 采用微信支付**服务商模式 + 分账（profit sharing）**：用户付款进入平台服务商商户号后，按单自动分账至服务者子商户号，平台抽成即分账比例；争议冻结用分账冻结实现。结算资金全程不沉淀在平台自有账户。P0 支付架构必须按此设计，影响订单/结算数据模型 |
| **人脸核身接口类目限制** | 清单的"平台认可认证"包含"实名+人脸"。微信"人脸核身"官方接口仅对政务、金融、医疗等特定类目开放，社区生活服务类目通常申请不到 | 认证降级为现实可行方案：身份证 OCR + 手机号三要素核验 + 自拍活体照片人工比对抽验；对外文案避免宣称"已通过官方人脸核身"。功能目标（证明"是本人在做服务"）不变，实现手段调整 |
| **未成年人信息合规** | 接娃场景收集儿童姓名、学校、路线、照片，属未成年人敏感个人信息，需监护人同意并最小化 | 接娃订单强制由监护人账号发起并签署知情同意书；儿童信息仅在订单生命周期内对订单双方可见，订单关闭后按期限脱敏；交接照片设置自动清理策略 |
| **小程序主体与类目资质** | 个人主体小程序无法开通微信支付；家政、陪诊相关类目可能要求资质材料；类目选错会被驳回 | 以**公司主体**注册小程序与微信支付商户号；类目按"生活服务"准备资质；C类机构入驻收取证照；陪诊相关页面文案避开"医疗服务"类目表述，定位为"陪同办事"性质 |
| **保险落地缺一环** | 服务者端有"确认平台责任险覆盖范围"，但保费承担、按单/按年投保、理赔流程未定，承诺无法兑现就是口碑风险 | P0 先上线下单页固定展示保障说明（保额、免赔、免责条款）；冷启动期用年度公众责任险兜底；P1 再接按单投保 API 并纳入"保险与抽成配置" |

## 三、对 P0 范围的修订建议

在原 12 项闭环基础上，**纳入以下 2 项 P0**（均为上线必要条件而非增强项）：

1. **站内订单沟通（轻量版）** —— 证据链闭环的必要条件，缺了它第 5、6、11 项的纠纷处理机制失效；
2. **隐私政策与敏感字段单独授权** —— 收集身份证/健康/儿童信息的上线合规前提。

同时明确一项**实现方式修订**（不新增功能点）：第 7 项"低偿线上支付+即时结算"按微信支付服务商分账架构实现，规避二清风险。

修订后第一版闭环为 14 项。

## 四、下一步建议（按依赖顺序）

1. **确认支付架构**：微信支付服务商分账模式的商户号申请与子商户进件流程周期较长（数周），应最先启动；
2. **数据模型初稿**：住户/楼栋/服务者/认证层级/订单/协议签署/凭证/信用流水/纠纷工单/审计日志 十类核心实体及关系；
3. **协议模板定稿**：宠物寄养、上门家政、接送、陪诊四份协议文本是责任边界核心，建议法务先行；
4. **原型验证**：先做"发布 → 接单 → 凭证 → 结算"一条链路的可点原型，验证 A 类场景的最小体验。
