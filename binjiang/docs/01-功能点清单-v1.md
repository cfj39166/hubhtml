# 功能点清单 v1（功能基线）

> 项目：社区 · 邻里服务
> 日期：2026-11-06
> 说明：本清单为功能基线，按"端 + 公共能力"组织，每个功能点标明设计理由与优先级。
> 优先级定义：**P0** = 第一版必须做；**P1** = 试点跑通后做；**P2** = 规模化再做。
> 评审修订见 [02-清单评审与合规补充-v1.md](02-清单评审与合规补充-v1.md)。

---

## 一、用户端（居民小程序）

| 功能点 | 具体设计 | 这么设计的理由 | 优先级 |
|---|---|---|---|
| 住户核验注册 | 手机号+楼栋房号核验，对接物业住户数据或上传房产/租赁证明，人工/自动审核 | 100栋楼陌生人社会，先确认"真实邻居"才敢开放服务 | P0 |
| 场景化首页入口 | 不按品类罗列，按"取快递、扔垃圾、出门喂猫、接娃来不及、找保洁"场景入口 | 用户想的是场景不是品类，降低发布门槛 | P0 |
| 服务分级展示 | A类低风险、B类中风险、C类机构服务分区展示，C类不开放个人接单 | 风险不同，准入门槛和协议必须不同 | P0 |
| 需求发布表单 | 极简表单+风险强制字段：时间、地点、价格、宠物健康/用药、接娃学校/交接方式、是否涉及钥匙证件 | 风险信息前置收集，减少纠纷举证难 | P0 |
| 智能匹配排序 | 同楼栋→同片区→全小区；A类优先同楼栋，B类可全小区 | 100栋楼匹配半径过大没人接，物理距离就是信任补充 | P0 |
| 服务者卡片 | 展示三层标识：真实邻居、平台认可、社区信赖；显示完成单量、评价、可接品类 | 让居民一眼判断"能不能信" | P0 |
| 订单凭证页 | 服务前/中/后拍照上传，自动时间戳；接娃/钥匙交接生成确认码 | 纠纷处理靠证据链，不靠口头约定 | P0 |
| 标准协议签署 | B类订单下单前强制签署对应协议模板：宠物寄养、上门家政、接送、陪诊 | 平台做居间撮合+凭证留存，必须书面化责任边界 | P0 |
| 低偿支付与结算 | 平台给指导价，支持线上支付，完成后即时到账服务者，平台低抽成 | 免费制造人情债，市场化定价失去邻里意义，低偿最可持续 | P0 |
| 双向评价与投诉 | 需求方评服务者，服务者也评需求方；恶意差评、放鸽子扣信用 | 只约束服务者会摧毁供给意愿 | P0 |
| 消息通知 | 微信模板消息/短信：接单、出发、到达、完成、异常提醒 | 社区服务高频短时，通知不及时体验断裂 | P0 |
| 地址与隐私脱敏 | 发布时只显示楼栋/片区，接单后才显示具体门牌；取件码脱敏 | 防止信息滥用和骚扰 | P0 |
| 常需服务订阅 | 固定时间代取快递、固定路线接娃拼单、定期保洁可设"常用订单" | 社区需求重复性强，降低重复发布成本 | P1 |
| 工具/闲置共享 | 电钻、梯子、露营装备等借还，押金或信用免押，归还确认 | 低风险高频，适合冷启动拉活跃 | P1 |
| 拼单/轮值工具 | 接娃拼单、团购自提、寒暑假看护拼班，平台只做协调和确认 | 平台不替代监护责任，只做组织工具 | P1 |
| C类机构入口 | 托育、养老、持证家政展示资质、价格、评价，跳转预约 | 高风险需求引导至机构，不让个人以互助名义承接 | P1 |
| 信用中心 | 展示自己的信任等级、完成单、协议记录、违约记录 | 信用可见才有约束力 | P1 |

## 二、服务者端（居民服务者/机构）

| 功能点 | 具体设计 | 这么设计的理由 | 优先级 |
|---|---|---|---|
| 分层认证入驻 | 真实邻居认证→平台认可认证（实名+人脸+无犯罪承诺+品类资质）→社区信赖等级 | 实名只证明存在，分层才证明可靠 | P0 |
| 可接品类开关 | 按认证等级开放A/B类；C类只对机构开放 | 防止低认证接高风险单 | P0 |
| 接单大厅 | 按楼栋/片区筛选，显示距离、价格、风险标签 | 服务者顺手接单，跨半小区意愿低 | P0 |
| 资质上传与到期提醒 | 健康证、居家上门服务证、无犯罪记录、养宠经验证明；到期自动停接 | 合规动态管理，避免证件过期仍接单 | P0 |
| 协议与保险确认 | 接B类单前签署服务者版协议，确认平台责任险覆盖范围 | 明确平台是居间方，不是服务提供方 | P0 |
| 服务过程留痕 | 出发打卡、到达拍照、完成拍照、异常上报 | 与用户端凭证形成双向证据链 | P0 |
| 收入与结算 | 订单收入、平台抽成明细、提现、争议冻结 | 即时回报是最有效激励 | P0 |
| 服务者评价与申诉 | 查看评价、对恶意差评申诉、信用分变动记录 | 双向公平，保护供给端 | P1 |

> 注：服务者端的通知（接单、结算、资质到期）复用用户端"消息通知"能力，见评审文档的合并建议。

## 三、楼栋协调人端（100栋楼的关键设计）

| 功能点 | 具体设计 | 这么设计的理由 | 优先级 |
|---|---|---|---|
| 楼栋协调人身份 | 每栋楼/几个单元设1名，物业管家或热心居民兼任，后台授权 | 100栋楼不能靠一个大群，必须有本地支点 | P0 |
| 本楼需求初审 | 查看本楼新发布需求，标记异常/高风险，提醒补充信息 | 第一时间降低风险，比平台远程审核快 | P0 |
| 服务者推荐 | 向本楼居民推荐已认证的本楼服务者 | 熟人推荐是冷启动最有效信任来源 | P0 |
| 纠纷初调 | 接收本楼简单纠纷工单，先协调，升级平台 | 小纠纷楼内解决，降低平台运营成本 | P1 |
| 楼栋看板 | 本楼需求数、接单率、活跃服务者、未闭环订单 | 指导楼栋运营，不靠感觉推广 | P1 |
| 楼栋开通开关 | 后台按楼栋/片区开启服务，未开通楼栋只能浏览不能发单 | 供给先行，避免"发了没人接" | P0 |

## 四、管理后台（平台运营）

| 功能点 | 具体设计 | 这么设计的理由 | 优先级 |
|---|---|---|---|
| 住户与服务者审核 | 住户核验、实名/人脸、无犯罪承诺、品类资质审核队列 | 信任机制的地基 | P0 |
| 服务品类与风险配置 | 配置A/B/C类、每类必填字段、协议模板、准入门槛、指导价 | 风险分级要可配置，不能写死 | P0 |
| 风险订单预警 | 未成年接送、多日宠物寄养、老人陪护、钥匙证件、高额报酬自动标记人工复核 | 高风险单必须拦截或加审 | P0 |
| 协议模板管理 | 宠物寄养、家政上门、接送、陪诊、跑腿代办模板版本管理 | 书面协议是责任边界核心 | P0 |
| 纠纷工单池 | 统一受理、SLA计时、证据查看、责任判定、闭环记录 | 纠纷不闭环会迅速摧毁口碑 | P0 |
| 信用分规则配置 | 完成单、评价、违约、恶意行为、申诉的加减分规则 | 动态信用比静态认证有约束力 | P1 |
| 供需热力图 | 分楼栋/片区看需求品类、接单率、供给缺口 | 指导先开哪栋楼、招哪类服务者 | P1 |
| 机构管理 | C类机构资质、合同、评价、下架管理 | 高风险服务只做入口和筛选 | P1 |
| 保险与抽成配置 | 平台责任险、订单险、抽成比例、退款规则 | 低偿模式必须控制成本和风险 | P1 |
| 内容与违禁风控 | 违禁词、异常报酬、包裹来源声明、代取违禁品拦截 | 防止跑腿代取被利用 | P0 |
| 数据看板 | 订单闭环率、复购率、纠纷率、楼栋活跃度、服务者留存 | 用数据决定扩展，不靠拍脑袋 | P2 |

## 五、公共能力与风控功能

| 功能点 | 具体设计 | 这么设计的理由 | 优先级 |
|---|---|---|---|
| 三层信任标识 | 真实邻居、平台认可、社区信赖，用户端可见 | 100栋楼陌生人场景，信任必须可视化 | P0 |
| 双向信用约束 | 需求方和服务者都受信用分约束 | 只罚服务者会导致供给流失 | P0 |
| 高风险红线拦截 | 长期看孩子、失能老人照护、医疗行为不允许个人接单，强制转C类入口 | 合规红线，避免平台变"黑托管" | P0 |
| 宠物寄养专项流程 | 健康申报、用药说明、服务前后照片、紧急医疗授权与费用上限 | 宠物纠纷举证难，必须专项设计 | P0 |
| 接娃专项流程 | 固定路线、实时位置共享、家长确认码、交接拍照、仅短时过渡 | 未成年安全是最高风险 | P0 |
| 包裹来源声明 | 代取快递需声明来源，异常高报酬订单预警 | 防止被利用代取不明包裹 | P0 |
| 证据链留存 | 照片、时间戳、确认码、协议签署记录、聊天记录统一归档 | 平台居间责任靠证据链自保 | P0 |
| 隐私与权限分级 | 楼栋协调人只看本楼，平台按角色授权，门牌接单后可见 | 防止内部信息滥用 | P0 |
| 支付与争议冻结 | 争议订单资金冻结，确认后释放 | 低偿也要有交易保障 | P0 |
| 微信小程序优先 | 不做独立App，管理后台Web，服务者端复用小程序 | 社区低频多场景，小程序摩擦最低 | P0 |

## 六、第一版最小闭环（P0功能组合）

**只做这些就能跑通：**
1. 住户核验注册；
2. 场景化首页 + A类服务发布；
3. 同楼栋/同片区匹配；
4. 三层信任标识；
5. 订单凭证拍照+时间戳；
6. B类协议强制签署；
7. 低偿线上支付+即时结算；
8. 双向评价+投诉；
9. 服务者分层认证+资质到期提醒；
10. 楼栋协调人+楼栋开通开关；
11. 风险订单预警+纠纷工单；
12. 高风险红线拦截+C类机构入口占位。

**第一版不做：** 邻里社交动态、积分商城、排行榜、复杂AI匹配、独立App、全小区统一大池子。原因很简单：供给密度和信任基础不足时，这些功能只会增加噪音，不会增加闭环。
